# Задание 1. Логгер на основе паттерна Singleton

## Описание

Реализован класс `Logger` — логгер на основе паттерна Singleton,
записывающий сообщения в файл. Логгер лежит в `common/` и собирается
как статическая библиотека, подключаемая ко всем заданиям лабораторной.

## Файлы

- `../common/logger.h` — объявление класса `Logger`
- `../common/logger.cpp` — реализация класса `Logger`
- `main.cpp` — тестирование логгера
- `README.md` — этот файл

## Функции

| Метод | Назначение |
|---|---|
| `static Logger& getInstance(const std::string& filename)` | возвращает ссылку на единственный экземпляр |
| `void log(const std::string& message, int level)` | записывает сообщение в файл, если его уровень не выше текущего |
| `void setLevel(int level)` | устанавливает текущий уровень логирования |
| `void setFile(const std::string& filename)` | переключает вывод в другой файл |
| `~Logger()` | закрывает файл |

## Ответы на вопросы

### 1. Почему метод `getInstance()` должен быть статическим?

Потому что он вызывается **до создания объекта класса**. Экземпляр
создаётся **внутри** этого метода (статическая локальная переменная),
значит, чтобы получить доступ к нему, нужен метод, который не требует
существующего объекта. Статический метод принадлежит классу, а не
конкретному экземпляру. Плюс он гарантирует единый глобальный доступ
к единственному объекту из любой точки программы.

### 2. Зачем удалены копирующий конструктор и оператор присваивания?

Паттерн Singleton гарантирует **единственный** объект класса. Если бы
копирующий конструктор и `operator=` остались доступными, можно было бы
сделать так:

```cpp
Logger copy = Logger::getInstance();  // копия — второй логгер
Logger other; other = Logger::getInstance();
```

Получилось бы несколько независимых логгеров, и сообщения писались бы
в разные файлы или с разным уровнем. Удаляя эти методы (`= delete`),
компилятор просто запрещает такие операции — Singleton остаётся
действительно единственным.

### 3. Когда создаётся и когда уничтожается статический объект внутри `getInstance()`? В какой момент закрывается файл?

Статическая локальная переменная создаётся **при первом вызове**
`getInstance()` — и именно в этот момент вызывается приватный конструктор,
который открывает файл. Уничтожается она **в конце программы**, после
выхода из `main()`, при разрушении статических объектов. Тогда вызывается
деструктор `Logger`, который закрывает файл.

Это гарантирует, что даже если `getInstance()` ни разу не вызвать,
файл не откроется, а если вызвать — он корректно закроется при завершении
программы.

### 4. Что происходит с аргументом `filename` при втором вызове `getInstance()`? Зачем поэтому понадобился `setFile()`?

При втором вызове аргумент `filename` **игнорируется**: статическая
переменная уже создана, и конструктор больше не вызывается. Поэтому
сменить файл через `getInstance("new.log")` нельзя.

Именно для этого нужен `setFile()`: он закрывает текущий файл и открывает
новый на перезапись. Так все последующие сообщения попадут в новый файл.

### 5. Как работает фильтрация по уровню? Фрагмент лога до и после `setLevel()`

Уровни: `ERROR = 0`, `WARNING = 1`, `INFO = 2`, `DEBUG = 3`.
Чем меньше число — тем важнее сообщение. В методе `log()` стоит проверка:

```cpp
if (level > currentLevel) return;
```

То есть сообщение записывается, только если его уровень **не выше**
текущего порога.

До `setLevel(WARNING)` (уровень `DEBUG`):
```
[2026-10-15 19:08:15] [ERROR] ERROR message
[2026-10-15 19:08:15] [WARNING] WARNING message
[2026-10-15 19:08:15] [INFO] INFO message
[2026-10-15 19:08:15] [DEBUG] DEBUG message
```

После `setLevel(WARNING)`:
```
[2026-10-15 19:08:15] [ERROR] ERROR после setLevel(WARNING)
[2026-10-15 19:08:15] [WARNING] WARNING после setLevel(WARNING)
```

`INFO` и `DEBUG` в лог не попали — их уровень выше порога `WARNING`.

### 6. Безопасна ли инициализация статической локальной переменной, если `getInstance()` одновременно вызовут несколько потоков (начиная с C++11)?

Да, безопасна. Начиная с **C++11** инициализация статических локальных
переменных потокобезопасна: компилятор гарантирует, что конструктор
выполнится **ровно один раз**, даже если несколько потоков войдут в
`getInstance()` одновременно. Остальные потоки будут ждать завершения
инициализации. Это зафиксировано в стандарте (раздел о «magic statics»).
До C++11 такой гарантии не было, и Singleton требовал ручной
синхронизации.
