# Задание 4. Делегирующие конструкторы

## Описание

Конструкторы `TrackedString()` и `TrackedString(const char*)` переделаны
в **делегирующие**: они не пишут логику создания объекта сами, а передают
её целевому конструктору `TrackedString(const std::string&)`. Это
позволяет избежать дублирования кода инициализации.

## Файлы

- `tracked_string.h` — копия из `02_task` (без изменений)
- `tracked_string.cpp` — доработан: `default` и `cstr` стали делегирующими
- `main.cpp` — демонстрация: `x` через default, `y` через cstr
- `README.md` — этот файл

## Функции

| Конструктор | Тип | Делегирует в |
|---|---|---|
| `TrackedString()` | делегирующий | `TrackedString(std::string{})` |
| `TrackedString(const char*)` | делегирующий | `TrackedString(std::string(s))` |
| `TrackedString(const std::string&)` | **целевой** | — |

## Ответы на вопросы

### 1. Порядок вызовов делегирующих конструкторов (по логу)

**`TrackedString x;`** (default ctor):
```
[string ctor (target)]      id=1 value="" alive=1
[default ctor (delegating)] this=... alive=1
```
Создание проходит через **два** конструктора:
`default` → делегирует в `string`.

**`TrackedString y("test");`** (cstr ctor):
```
[string ctor (target)]    id=2 value="test" alive=2
[cstr ctor (delegating)]  id=2 alive=2
```
Создание проходит через **два** конструктора:
`cstr` → делегирует в `string`.

**Важно:** делегирующий конструктор сначала **полностью выполняет целевой**
(включая тело), и только потом — своё собственное тело. Поэтому в логе
`string ctor (target)` всегда идёт **первым**, а `default ctor (delegating)`
или `cstr ctor (delegating)` — **вторым**.

Объект `x` создаётся через:
1. `TrackedString(std::string{})` — целевой, задаёт `id_ = 1`, `aliveCount_ = 1`;
2. `TrackedString()` — делегирующий, пишет лог, больше ничего не делает.

### 2. Чем делегирование отличается от вызова `init()` из тела?

| | Делегирование | Вспомогательный `init()` |
|---|---|---|
| Место вызова | в списке инициализации | в теле конструктора |
| Порядок | целевой конструктор работает **до** тела делегирующего | `init()` работает **после** инициализации полей |
| Возможность инициализировать `const`-поля и ссылки | да | нет |
| Возможность инициализировать базовые классы | да | нет |
| Возможность присвоить `id_` в нашем случае | `id_` задаётся **один раз** в целевом | пришлось бы добавлять проверку «а не инициализирован ли уже» |
| Типобезопасность | выше — это конструктор | ниже — обычный метод |

Главное отличие: **делегирование — это инициализация**, `init()` — **присваивание после** того, как поля уже сконструированы по умолчанию.
Именно поэтому вариант A в задании 3 создавал лишний объект.

Кроме того, при делегировании объект создаётся **один раз** — собственно,
это и есть цель. Вспомогательный метод не отменяет дефолтную
инициализацию полей.

### 3. Почему делегирование возможно только в списке инициализации?

Потому что **делегирование — это разновидность инициализации**. В C++
конструктор должен быть вызван **до** того, как начнёт выполняться его
тело. Список инициализации — это то место, где компилятор видит, каким
именно конструктором инициализировать объект.

Если бы делегирование было в теле (`TrackedString() { TrackedString(""); }`),
это означало бы: «создай **второй, временный** объект внутри тела».
Это не делегирование, а создание временного объекта, после которого
пришлось бы что-то делать с уже сконструированным `this`.

Правило простое: **всё, что касается «как создать объект», должно быть
в списке инициализации**. В теле конструктора объект уже существует,
и его поля уже инициализированы.
