# Задание 3. Особенности вещественных чисел

## Часть 1. Представление чисел в IEEE 754

Тип `float` занимает 32 бита и устроен по стандарту IEEE 754 так:

```
бит 31      биты 30..23         биты 22..0
[знак]      [порядок, 8 бит]    [мантисса, 23 бита]
   s              e                    m
```

Значение числа: `(−1)^s × 1.m × 2^(e − 127)`, где `e` — «смещённый» порядок (bias = 127), а `1.m` — мантисса с неявной ведущей единицей.

### (а) Число 10.25

Переводим в двоичный вид:

```
10.25 = 1010.01₂  (10 = 1010₂; 0.25 = 0.01₂)
      = 1.01001₂ × 2³
```

Нормируем (ведущая единица перед точкой):

- **Знак:** число положительное → `s = 0`.
- **Порядок:** `e = 3 + 127 = 130 = 10000010₂`.
- **Мантисса:** отбрасываем ведущую `1.` → `01001000000000000000000₂` = `0x40000`.

Итого биты:

```
0 10000010 01001000000000000000000
s    e            m
```

Проверка: `1.01001₂ × 2³ = 1010.01₂ = 10.25` — точно.

### (б) Число 7.1

```
7.1 = 111.00011001100110011001100...₂
```

Дробная часть `0.1` в двоичной — **периодическая** (`0.0001100110011...`), поэтому ровно во `float` она не помещается. Нормируем:

```
7.1 = 1.110001100110011001100...₂ × 2²
```

- **Знак:** `s = 0`.
- **Порядок:** `e = 2 + 127 = 129 = 10000001₂`.
- **Мантисса:** округляем до 23 бит → `11000110011001100110011₂` = `0x633333`.

Итого биты:

```
0 10000001 11000110011001100110011
```

Число `7.1` во `float` **не представимо точно** — хранится ближайшее приближение. Именно поэтому при вычислениях появляются «хвосты» в младших разрядах.

### (в) Сумма 10.25 + 7.1

Программа выводит с `setprecision(12)`:

```
10.25 + 7.1 = 17.3500003815
```

Точный математический результат — `17.35`. Расхождение объясняется тем, что `7.1f` хранится как приближение (см. пункт (б)), и эта ошибка складывается с точным `10.25`. Результат — ближайшее к `17.35` значение, представимое во `float`, но не само `17.35`. Ошибка порядка `4 × 10⁻⁷` — это и есть накопленная погрешность представления `7.1`.

## Часть 2. Нарушение ассоциативности

Программа демонстрирует:

```cpp
float a = 1.0e20f;
float b = -1.0e20f;
float c = 1.0f;

float r1 = (a + b) + c;   // = 1
float r2 = a + (b + c);   // = 0
```

Результаты:

```
(a + b) + c = 1
a + (b + c) = 0
equal? no
```

**Почему так происходит.**

- В первом случае: `(1e20 + (−1e20)) + 1 = 0 + 1 = 1` — точно.
- Во втором случае: `b + c = −1e20 + 1`. Но `1e20` при `float`-точности имеет порядок `2^66`, поэтому шаг между соседними представимыми числами в этом диапазоне гораздо больше `1`. При сложении `−1e20 + 1` младшая единица **не помещается** в мантиссу и теряется: результат равен `−1e20`. Затем `a + (−1e20) = 0`.

Итого: `1 ≠ 0` — операция сложения во `float` **не ассоциативна**. Это прямое следствие ограниченной точности представления чисел с плавающей точкой.

## Часть 3. Почему `==` для вещественных чисел небезопасно

Программа показывает классический пример:

```cpp
float x = 0.1f + 0.2f;   // 0.300000011920928955078125
float y = 0.3f;          // 0.300000011920928955078125
x == y                   // false!
```

Числа `0.1`, `0.2` и `0.3` в двоичной системе счисления — **периодические дроби**, они не представимы точно ни во `float`, ни в `double`. Каждое из них хранится как **приближение** с некоторой ошибкой округления. При сложении `0.1f + 0.2f` эти ошибки складываются, и результат **побитово не совпадает** с `0.3f`, хотя визуально (при 12 знаках) они выглядят одинаково:

```
x = 0.300000011921
y = 0.300000011921
```

Строгое сравнение `x == y` даёт `false`, потому что числа различаются в младших битах.

**К чему это может привести на практике.** Логика, построенная на `==` для вещественных чисел, может «ломаться» непредсказуемым образом: например, условие `if (a + b == c)` не сработает, хотя математически должно. Такие ошибки тяжело отлаживать, потому что визуально числа «одинаковые».

**Правильный подход** — сравнивать с **эпсилоном** (допуском):

```cpp
std::fabs(x - y) < 1e-6f
```

Программа это демонстрирует: `|x − y| ≈ 3 × 10⁻⁸`, что меньше `1e-6`, поэтому «почти равны» — `true`. Величину эпсилона выбирают в зависимости от задачи: слишком большой — можно пропустить реальное различие; слишком маленький — можно получить ложное «не равно» из-за накопленных погрешностей.
