# Задание 1. Представление целых чисел. Битовые операции

## Часть 1. Вывод 32-битного представления числа +42

Число `42` в двоичном виде:

```
42 = 32 + 8 + 2 = 2^5 + 2^3 + 2^1 = 0b101010
```

В 32-битном представлении (`uint32_t`):

```
00000000 00000000 00000000 00101010
```

Функция `print_bits` идёт по битам от старшего (31-го) к младшему (0-му), сдвигая число вправо на `i` позиций и оставляя младший бит через `& 1U`.

## Часть 2. Битовые операции для a = 42, b = −17

Для удобства оба числа приведены к `uint32_t`. Отрицательное число `−17` хранится в дополнительном коде:

```
a = 42  = 00000000 00000000 00000000 00101010
b = −17 = 11111111 11111111 11111111 11101111
```

### 1. `a & b` — побитовое И

Результат — единица там, где **оба** бита равны 1:

```
a: 00000000 00000000 00000000 00101010
b: 11111111 11111111 11111111 11101111
&: 00000000 00000000 00000000 00101010
```

Результат: `00000000 00000000 00000000 00101010` = **42**.

Логика: у `b` в младших битах стоят единицы почти везде, но в битах, соответствующих `a`, «совпадают» только те, где и у `a` стоит 1. Поскольку `a = 42` имеет всего три единичных бита, а у `b` эти же позиции тоже равны 1, результат совпадает с `a`.

### 2. `a | b` — побитовое ИЛИ

Результат — единица там, где **хотя бы один** бит равен 1:

```
a: 00000000 00000000 00000000 00101010
b: 11111111 11111111 11111111 11101111
|: 11111111 11111111 11111111 11101111
```

Результат: `11111111 11111111 11111111 11101111` = **4294967279** (это `b` в беззнаковой интерпретации).

Логика: у `b` почти все биты = 1, а у `a` единицы только в младших разрядах. ИЛИ «заполняет» единицами всё, где есть хотя бы одна единица. Единственный нулевой бит `b` — 4-й (значение `16`) — остаётся нулевым, потому что у `a` там тоже 0.

### 3. `a ^ b` — побитовое исключающее ИЛИ (XOR)

Результат — единица там, где биты **различаются**:

```
a: 00000000 00000000 00000000 00101010
b: 11111111 11111111 11111111 11101111
^: 11111111 11111111 11111111 11000101
```

Результат: `11111111 11111111 11111111 11000101` = **4294967237**.

Логика: XOR «инвертирует» те биты `a`, где у `b` стоит 1. Поскольку у `b` в старших 27 битах — единицы, они инвертируют нули `a` в единицы. В младших битах сравнение идёт «по различию».

### 4. `~a` — побитовое НЕ (инверсия)

Все биты переворачиваются:

```
a:  00000000 00000000 00000000 00101010
~a: 11111111 11111111 11111111 11010101
```

Результат: `11111111 11111111 11111111 11010101` = **4294967253**.

Если интерпретировать как `int32_t`, это `−43` (потому что `~x = −x − 1` для знаковых).

### 5. `a << 2` — сдвиг влево на 2

Все биты сдвигаются влево, младшие заполняются нулями:

```
a:      00000000 00000000 00000000 00101010
a << 2: 00000000 00000000 00000000 10101000
```

Результат: `10101000` = `168` = `42 × 4`. Сдвиг влево на `n` эквивалентен умножению на `2^n`.

### 6. `a >> 2` — сдвиг вправо на 2

Для беззнакового числа — логический сдвиг, старшие биты заполняются нулями:

```
a:      00000000 00000000 00000000 00101010
a >> 2: 00000000 00000000 00000000 00001010
```

Результат: `00001010` = `10` = `42 / 4` (целочисленное деление).

### 7. `b << 2` — сдвиг влево на 2

```
b:      11111111 11111111 11111111 11101111
b << 2: 11111111 11111111 11111111 10111100
```

Результат: `11111111 11111111 11111111 10111100` = **4294967228**.

Если интерпретировать как `int32_t`: `−68` = `−17 × 4`. Сдвиг влево для отрицательных работает так же, как умножение на степень двойки (при отсутствии переполнения).

### 8. `b >> 2` — сдвиг вправо на 2

Поскольку `b` у нас `uint32_t` — сдвиг **логический**, старшие биты заполняются нулями:

```
b:      11111111 11111111 11111111 11101111
b >> 2: 00111111 11111111 11111111 11111011
```

Результат: `00111111 11111111 11111111 11111011` = **1073741819**.

Важно: если бы `b` был `int32_t`, сдвиг был бы **арифметическим** — старшие биты заполнялись бы единицами, и результат остался бы отрицательным (`−5`). Это разбирается в вопросе 4.

## Вопрос 1. Пояснение результатов (см. выше)

## Вопрос 2. Чему равно −1 в 32-битном представлении?

**Прямой код** (`−1`): старший бит = 1 (знак), остальные — модуль числа:

```
1 0000000 00000000 00000000 00000001
```

**Обратный код**: все биты модуля инвертируются, знаковый бит остаётся 1:

```
1 1111111 11111111 11111111 11111110
```

**Дополнительный код**: к обратному коду прибавляется 1:

```
1 1111111 11111111 11111111 11111110
+                                     1
= 11111111 11111111 11111111 11111111
```

Итого `−1` в 32-битном дополнительном коде — это **все единицы**:

```
11111111 11111111 11111111 11111111
```

## Вопрос 3. Как устроен дополнительный код? Почему он появился?

**Устройство.** Дополнительный код отрицательного числа `−x` получается так:
1. Берём модуль `x` в двоичном виде.
2. Инвертируем все биты (получаем обратный код).
3. Прибавляем 1.

Формально: `−x = ~x + 1`.

Пример для `−17`:
```
17      = 00000000 00000000 00000000 00010001
~17     = 11111111 11111111 11111111 11101110
~17 + 1 = 11111111 11111111 11111111 11101111   ← это −17
```

**Почему появился.** Прямой код неудобен:
- Есть «двойной ноль»: `+0 = 000...0` и `−0 = 100...0`. Два разных представления одного числа.
- Сложение и вычитание требуют разной логики: нужно анализировать знаки и выбирать операцию. Это усложняет схему процессора.

Дополнительный код решает обе проблемы:
- **Единственный ноль**: `000...0`.
- **Вычитание = сложение с дополнением**: `a − b = a + (−b)`, причём знаковый бит обрабатывается автоматически. Одна и та же схема сумматора работает и для сложения, и для вычитания.
- Диапазон `int32_t` получается асимметричным: `[−2^31, 2^31 − 1]`, потому что `100...0` отдано под `−2^31`.

## Вопрос 4. Почему при сдвиге вправо отрицательных чисел результат остаётся отрицательным?

Для **знаковых** типов (`int32_t`) операция `>>` — это **арифметический сдвиг вправо**:
- Все биты сдвигаются вправо.
- Освободившиеся старшие биты заполняются **знаковым битом** (для отрицательных — единицами).

Пример для `−17` как `int32_t`:
```
−17     = 11111111 11111111 11111111 11101111
−17 >> 2= 11111111 11111111 11111111 11111011
```

Старшие два бита заполнились единицами, поэтому знаковый бит (31-й) остался `1` — число остаётся отрицательным. В десятичном виде это `−5`, что совпадает с `−17 / 4` при округлении к минус бесконечности.

Для **беззнаковых** типов (`uint32_t`) `>>` — это **логический сдвиг**: старшие биты заполняются нулями. Именно это мы и видим в нашем коде: `b >> 2 = 1073741819`, потому что `b` объявлен как `uint32_t`.

Стандарт C++ (начиная с C++20) формально гарантирует арифметический сдвиг вправо для знаковых чисел. До C++20 это было implementation-defined, но на практике все современные компиляторы делали именно арифметический сдвиг.
