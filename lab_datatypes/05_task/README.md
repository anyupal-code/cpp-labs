# Задание 5. Влияние типа данных на скорость вычислений

## Условия эксперимента

- **N = 10⁸ итераций** в каждом замере.
- Каждый замер: `x += 1` в цикле.
- Типы: `char`, `short`, `int`, `unsigned char`, `unsigned short`, `unsigned int`, `float`, `double`.
- Две версии:
    - **с `volatile`** — переменная `x` помечена `volatile`, компилятор не может её оптимизировать;
    - **без `volatile`** — переменная обычная, но после цикла стоит проверка `if (x == -123)`, чтобы компилятор не выкинул цикл целиком.
- **Замеры проведены в профиле Release (`-O2`/`-O3`).** Профиль Debug не использовался: в нём оптимизации отключены, поэтому `volatile` и «без» дают почти одинаковые времена и не позволяют увидеть влияние оптимизаций на замер. Release показывает реальную картину.

## Вопрос 1. Как отличаются результаты с `volatile` и без?

**Разница принципиальная.**

**Без `volatile` (Release):**
- **Целые типы — `0.0 µs`.** Компилятор с `-O2` **полностью свернул цикл** из 10⁸ итераций в одно присваивание: `x = N`. Действительно, `0 + 1 + 1 + ... + 1` (N раз) = N, и для целых чисел эта оптимизация **безопасна** (переполнения нет, а если было бы — это UB, и компилятор вправе делать что угодно). Весь цикл исчез, замер бессмыслен.
- **`float` / `double` — ~98 тыс. µs, не ноль.** Компилятор **не свернул** цикл для вещественных типов, потому что **сложение с плавающей точкой не ассоциативно** (см. задание 3): `((0 + 1) + 1) + ...` ≠ `N` из-за накопления погрешности округления. Компилятор обязан честно выполнить все 10⁸ сложений.

**С `volatile`:**
- **Целые типы — ~135 тыс. µs.** Компилятор не имеет права оптимизировать: каждое `+= 1` — реальное чтение из памяти, сложение и запись обратно.
- **`float` / `double` — ~223 тыс. µs.** Ещё медленнее, чем без `volatile`, потому что теперь каждое сложение ходит в память.

**Вывод.** В Release `volatile`:
- **критически необходим** для целых — без него цикл исчезает и замер превращается в ноль;
- **не влияет на принципиальную возможность оптимизации** для вещественных — цикл не сворачивается в обоих случаях, но с `volatile` он ещё и медленнее из-за трафика с памятью.

## Вопрос 2. Зависит ли время выполнения от размера типа? Почему так может быть?

**Практически нет.** В замерах с `volatile` времена для `char`, `short`, `int` (1, 2, 4 байта) лежат в диапазоне 133–138 тыс. µs — разброс в пределах шума.

Причина:
- Процессор x86-64 работает с **32- и 64-битными регистрами**. Операция сложения всегда выполняется над 32/64 битами.
- `char` и `short` перед сложением расширяются до 32 бит, результат усекается обратно. Но эти расширение/усечение занимают **тот же такт**, что и обычное сложение, — на современных CPU это «бесплатно».
- Обращения к памяти при `volatile` для 1, 2, 4 байт **одинаково быстрые**, если данные в кэше.

## Вопрос 3. Как ведут себя `float` и `double` по сравнению с целыми?

**`float` / `double` медленнее целых, но по двум разным причинам в разных режимах.**

**С `volatile`:**
- целые: ~135 тыс. µs,
- `float`: ~223 тыс. µs,
- `double`: ~223 тыс. µs.
- `float` / `double` медленнее целых в ~1.7 раза. Причины:
    1. **FPU-сложение дороже** целочисленного: задержка ~3–5 тактов против 1, а с `volatile` зависимость через память не даёт конвейеру «спрятать» эту задержку.
    2. **Больший трафик с памятью** (4 и 8 байт против 4 у `int`).
- `float` и `double` дают **одинаковое** время. Значит, узкое место — не трафик с памятью (иначе `double` был бы медленнее), а задержка FPU-сложения. 4 или 8 байт — неважно.

**Без `volatile`:**
- целые: **0.0 µs** (цикл свёрнут),
- `float`: ~98 тыс. µs,
- `double`: ~98 тыс. µs.
- `float` / `double` **не свёрнуты**, потому что сложение с плавающей точкой **не ассоциативно**. Компилятор обязан выполнить все итерации.
- Время ~98 тыс. µs — меньше, чем с `volatile` (223 тыс.), потому что `x` теперь держится в регистре FPU, а не в памяти.
- `float` и `double` **снова одинаковы**.

**Итог.** `float` и `double` ведут себя **одинаково** между собой и **медленнее целых** в обоих режимах. Их нельзя «свернуть», поэтому они не обнуляются без `volatile`. Это прямое следствие неассоциативности операций с плавающей точкой.

## Вопрос 4. Влияет ли знаковость у целых типов на производительность?

**Нет.** Времена для `char` / `unsigned char`, `short` / `unsigned short`, `int` / `unsigned int` совпадают в пределах шума.

Причина: на уровне машинных инструкций **сложение одинаково** для знаковых и беззнаковых целых — процессор выполняет `add`, не различая типы. Разница была бы в:
- **сравнениях** (`jg`/`jl` против `ja`/`jb`),
- **сдвигах вправо** (`>>` для знаковых — арифметический, для беззнаковых — логический),
- **делении** (`/` для знаковых округляет к нулю, для беззнаковых — нет).

Но **сложение** одинаково, поэтому знаковость не влияет на скорость в этой работе.

## Общий вывод

В ходе работы:
- Проведены замеры времени сложения `x += 1` для 8 типов (3 знаковых, 3 беззнаковых, 2 вещественных) при N = 10⁸ итераций, в двух версиях — с `volatile` и без, в профиле Release.
- Показано, что **`volatile` критически важен**: без него компилятор полностью сворачивает цикл для целых типов, время падает до `0.0 µs`, замер становится бессмысленным.
- Обнаружено важное различие между целыми и вещественными типами: для **целых** цикл `x += 1` сводится к `x = N` (ассоциативность и отсутствие переполнения позволяют), а для **`float`/`double`** — нет, потому что сложение с плавающей точкой **не ассоциативно**.
- Установлено, что **размер целочисленного типа не влияет** на скорость сложения: на x86-64 все операции выполняются в 32/64-битных регистрах.
- Установлено, что **знаковость целых типов не влияет** на скорость сложения: инструкция `add` одинакова для `signed` и `unsigned`.
- Показано, что **`float` и `double` медленнее целых** (~1.7x с `volatile`) из-за большей задержки FPU и трафика с памятью. При этом `float` и `double` дают одинаковое время — узкое место в задержке FPU, а не в размере.
