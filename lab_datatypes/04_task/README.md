# Задание 4. Битовые vs арифметические операции

## Условия эксперимента

- **N = 10⁸ итераций** в каждом замере.
- Типы: `int32_t` и `uint32_t`.
- Все переменные помечены `volatile`, чтобы исключить оптимизации.
- Внутри цикла **восстанавливается исходное значение** `x = 123456789` (иначе за несколько итераций оно обнулилось бы, и операции стали бы «мгновенными»).
- Результат каждой операции сохраняется в `volatile sink`, чтобы компилятор не выкинул вычисление как «мёртвое».
- Для каждой пары (тип × операция) сделаны **два независимых замера**: арифметический вариант и битовый.

## Вопрос. Медленнее или быстрее битовая операция арифметической? В каких случаях да, в каких нет? Почему?

**Короткий ответ:** битовая операция **не всегда** быстрее. Всё зависит от того, может ли компилятор **сам** заменить арифметическую операцию на битовую, не нарушив семантику языка. Если может — разницы нет. Если не может — битовая выигрывает.

### Разбор по парам операций

**1. `x / 2` vs `x >> 1` для `int32_t` — сдвиг быстрее (~7%).**

- В C++ операция `/` для знакового числа — это **деление с округлением к нулю**.
- Операция `>>` для знакового числа — **арифметический сдвиг**, то есть округление к **−∞**.
- Для положительных результатов они совпадают, но для отрицательных — **разные**:
    - `−3 / 2 == −1`
    - `−3 >> 1 == −2`
- Поэтому компилятор **не имеет права** заменить `x / 2` на `x >> 1`, когда тип знаковый. Он вынужден использовать настоящую инструкцию деления (или длинную последовательность с коррекцией знака).
- Битовая операция `>>` — это **одна инструкция** `sar` (Shift Arithmetic Right), выполняется за 1 такт.
- Итог: в замерах `int32_t / 2` = 243796.6 µs, `int32_t >> 1` = 227150.8 µs. Разница ~7% — устойчивая, больше шума.

**2. `x / 2` vs `x >> 1` для `uint32_t` — разницы нет.**

- Для **беззнакового** числа `x / 2` и `x >> 1` **семантически эквивалентны** (оба округляют вниз, знака нет).
- Компилятор это знает и **сам** заменяет `/ 2` на сдвиг.
- В коде обе версии компилируются в **одну и ту же инструкцию** `shr`.
- Итог: 221148.3 µs vs 221595.3 µs — разница в пределах шума.

**3. `x * 2` vs `x << 1` — разницы нет ни для одного типа.**

- Умножение на степень двойки **эквивалентно** сдвигу влево для обоих типов.
- Компилятор сам заменяет `x * 2` на `shl`.
- Итог: `int32_t`: 222595.7 vs 227637.7 µs; `uint32_t`: 220664.5 vs 220435.7 µs — всё в пределах шума.

**4. `x % 2 == 0` vs `(x & 1) == 0` — разницы нет.**

- Для взятия остатка по модулю **степени двойки** компилятор сам использует битовую маску.
- `% 2` и `& 1` компилируются в одну и ту же инструкцию `and`.
- Итог: `int32_t`: 210194.3 vs 209309.6 µs; `uint32_t`: 221612.9 vs 207486.4 µs — небольшой разброс, но устойчивого преимущества нет.

### Общий вывод

**Битовая операция быстрее арифметической только в том случае, когда компилятор не может заменить одну на другую автоматически.** Это происходит, когда арифметическая семантика отличается от битовой — классический пример: `signed / 2` и `signed >> 1` для отрицательных чисел.

Когда арифметическая и битовая операции **семантически эквивалентны** (для беззнаковых, для умножения на степень двойки, для `% 2`), компилятор делает замену сам, и разницы в производительности нет — обе версии выполняются одной и той же машинной инструкцией.

## Важное замечание о шуме

Все значения в таблице лежат в диапазоне ~207–244 тыс. µs. Современные процессоры (x86-64) имеют:
- турбо-буст (частота плавает),
- кэши нескольких уровней,
- внеочередное исполнение,
- фоновые процессы ОС.

Из-за этого измерения имеют **разброс в несколько процентов**. Доверять стоит только **устойчивым** различиям, которые воспроизводятся при повторных запусках. В нашем случае устойчиво выделяется только одно: `int32_t / 2` медленнее, чем `int32_t >> 1`.
