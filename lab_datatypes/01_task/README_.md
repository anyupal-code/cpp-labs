# Задание 1. Представление целых чисел. Битовые операции

## Часть 1. Вывод 32-битного представления числа +42

42 = 32 + 8 + 2 = `101010`

В 32 битах:

```
00000000 00000000 00000000 00101010
```

Функция `print_bits` идёт от 31-го бита к 0-му: сдвигаем число на `i` вправо и берём младший бит через `& 1U`.

## Часть 2. Битовые операции для a = 42, b = −17

Оба числа приводим к `uint32_t`. Число −17 в дополнительном коде:

```
a = 42  = 00000000 00000000 00000000 00101010
b = −17 = 11111111 11111111 11111111 11101111
```

### 1. `a & b` — побитовое И

Единица там, где **оба** бита равны 1:

```
a: 00000000 00000000 00000000 00101010
b: 11111111 11111111 11111111 11101111
&: 00000000 00000000 00000000 00101010
```

Результат: **42**. У `a` всего три единичных бита, и у `b` на тех же местах тоже 1 — поэтому получилось само `a`.

### 2. `a | b` — побитовое ИЛИ

Единица там, где **хотя бы один** бит равен 1:

```
a: 00000000 00000000 00000000 00101010
b: 11111111 11111111 11111111 11101111
|: 11111111 11111111 11111111 11101111
```

Результат: **4294967279** (это `b` как беззнаковое). У `b` почти везде единицы, так что ИЛИ просто оставляет его. Единственный ноль `b` — 4-й бит (16) — остаётся нулём, потому что у `a` там тоже 0.

### 3. `a ^ b` — побитовое исключающее ИЛИ (XOR)

Единица там, где биты **различаются**:

```
a: 00000000 00000000 00000000 00101010
b: 11111111 11111111 11111111 11101111
^: 11111111 11111111 11111111 11000101
```

Результат: **4294967237**. XOR инвертирует биты `a` там, где у `b` стоит 1. В старших 27 битах у `b` единицы — они превращают нули `a` в единицы.

### 4. `~a` — побитовое НЕ (инверсия)

Все биты переворачиваются:

```
a:  00000000 00000000 00000000 00101010
~a: 11111111 11111111 11111111 11010101
```

Результат: **4294967253**. Как `int32_t` это **−43** (потому что `~x = −x − 1`).

### 5. `a << 2` — сдвиг влево на 2

Биты уезжают влево, младшие заполняются нулями:

```
a:      00000000 00000000 00000000 00101010
a << 2: 00000000 00000000 00000000 10101000
```

Результат: **168** = 42 × 4. Сдвиг влево на `n` = умножение на `2^n`.

### 6. `a >> 2` — сдвиг вправо на 2

Для беззнакового — логический сдвиг, старшие биты заполняются нулями:

```
a:      00000000 00000000 00000000 00101010
a >> 2: 00000000 00000000 00000000 00001010
```

Результат: **10** = 42 / 4 (целочисленное деление).

### 7. `b << 2` — сдвиг влево на 2

```
b:      11111111 11111111 11111111 11101111
b << 2: 11111111 11111111 11111111 10111100
```

Результат: **4294967228**. Как `int32_t` это **−68** = −17 × 4. Для отрицательных сдвиг влево работает как умножение на степень двойки (если нет переполнения).

### 8. `b >> 2` — сдвиг вправо на 2

`b` — это `uint32_t`, поэтому сдвиг **логический**, старшие биты заполняются нулями:

```
b:      11111111 11111111 11111111 11101111
b >> 2: 00111111 11111111 11111111 11111011
```

Результат: **1073741819**. Если бы `b` был `int32_t`, сдвиг был бы **арифметическим** — старшие биты заполнялись бы единицами, и результат остался бы отрицательным (**−5**). Это разбирается в вопросе 4.

## Вопрос 1. Пояснение результатов (см. выше)

Все результаты разобраны в пунктах 1–8 с битовыми выкладками.

## Вопрос 2. Чему равно −1 в 32-битном представлении?

**Прямой код** (−1): старший бит = 1 (знак), остальные — ноль:

```
1 0000000 00000000 00000000 00000001
```

**Обратный код**: биты модуля инвертируем, знаковый бит остаётся 1:

```
1 1111111 11111111 11111111 11111110
```

**Дополнительный код**: к обратному прибавляем 1:

```
1 1111111 11111111 11111111 11111110
+                                  1
= 11111111 11111111 11111111 11111111
```

Итого −1 в 32-битном дополнительном коде — это **все единицы**:

```
11111111 11111111 11111111 11111111
```

## Вопрос 3. Как устроен дополнительный код? Почему он появился?

**Устройство.** Отрицательное число `−x` получается так:

1. Берём модуль `x` в двоичном виде.
2. Инвертируем все биты (обратный код).
3. Прибавляем 1.

Формально: `−x = ~x + 1`.

Пример для −17:

```
17      = 00000000 00000000 00000000 00010001
~17     = 11111111 11111111 11111111 11101110
~17 + 1 = 11111111 11111111 11111111 11101111   ← это −17
```

**Почему появился.** Прямой код неудобен:

- Есть «двойной ноль»: `+0 = 000...0` и `−0 = 100...0`. Два разных представления одного числа.
- Сложение и вычитание требуют разной логики: нужно смотреть на знаки и выбирать операцию. Это усложняет схему процессора.

Дополнительный код решает обе проблемы:

- **Один ноль**: `000...0`.
- **Вычитание = сложение с дополнением**: `a − b = a + (−b)`, знаковый бит обрабатывается сам. Один и тот же сумматор годится и для сложения, и для вычитания.
- Диапазон `int32_t` получается несимметричным: `[−2^31, 2^31 − 1]`, потому что `100...0` отдано под `−2^31`.

## Вопрос 4. Почему при сдвиге вправо отрицательных чисел результат остаётся отрицательным?

Для **знаковых** (`int32_t`) операция `>>` — это **арифметический сдвиг вправо**:

- Все биты сдвигаются вправо.
- Освободившиеся старшие биты заполняются **знаковым битом** (для отрицательных — единицами).

Пример для −17 как `int32_t`:

```
−17      = 11111111 11111111 11111111 11101111
−17 >> 2 = 11111111 11111111 11111111 11111011
```

Старшие два бита заполнились единицами, знаковый бит (31-й) остался `1` — число по-прежнему отрицательное. В десятичном виде это **−5**, что совпадает с −17 / 4 при округлении к минус бесконечности.

Для **беззнаковых** (`uint32_t`) `>>` — это **логический сдвиг**: старшие биты заполняются нулями. Именно это мы видим в коде: `b >> 2 = 1073741819`, потому что `b` — `uint32_t`.

Стандарт C++ (с C++20) формально гарантирует арифметический сдвиг вправо для знаковых чисел. До C++20 это было implementation-defined, но на практике все современные компиляторы делали именно арифметический сдвиг.
